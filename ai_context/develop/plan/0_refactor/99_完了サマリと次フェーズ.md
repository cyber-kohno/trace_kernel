# 0_refactor 完了サマリと次フェーズ

## 位置づけ

`0_refactor` は、アプリモジュール資産の品質改善に向けた最初の土台整理フェーズとして実施した。  
本フェーズでは、機能追加ではなく、以下のような保守性・可読性・責務境界の改善を主眼に置いた。

- 命名の不安定さ解消
- 状態管理の責務分離
- UI レイヤーの役割整理
- 既存実装の重複削減
- 型チェック上のノイズ除去

現時点で、`0_refactor` は「ひと段落した」と判断してよい状態に到達している。

---

## 主な成果

### 1. 命名の整理

- `.ts` ファイルを `kebab-case` に統一
- `.svelte` ファイルの責務ベース命名を進行
- `MD*` / `PR*` の略称を廃止
- `MaintenanceMange` などの typo を修正
- `params` ディレクトリを `entries` へ整理

結果として、以前より「ファイル名から責務が読める」状態に近づいた。

### 2. Store の責務分離

- `app-store`
- `ui-store`
- `workspace-store`
- `workspace-validation-store`
- `cache-store`
- `invalidate-store`

を分離し、root store に集約されていた責務を段階的に解体した。  
特に `workspace` と `validation(disables)` を分離できたことは大きい。

### 3. 画面レイヤーの整理

以下のように、画面構成の名前と責務を揃えた。

- `WorkspaceSplitView`
- `WorkspaceEntryPane`
- `MaintenancePane`

また、`EntrySection` の導入により、entry 一覧の重複した描画パターンを共通化した。

### 4. Maintenance 系の共通化

`maintenance-helpers.ts` を追加し、各 `Maintenance*` 画面で重複していた

- target entry の取得
- workspace commit
- validation 実行

を整理した。  
これにより `MaintenanceEnv / Resource / Process / Work / Dataset` の実装スタイルがかなり揃った。

### 5. dataset 配下の整理

`dataset/choose/scan` 配下の命名と責務を見直し、以下へ整理した。

- `DatasetChoosePane`
- `DatasetChooseRow`
- `DatasetScanPane`
- `DatasetTargetListPane`
- `DirectoryFilterConditions`
- `FileFilterConditions`
- `dataset-choose-util`
- `dataset-scan-util`

加えて、`StoreDataset.DatasetPhase` を導入し、phase 名も揃えた。

### 6. チェック状態の改善

`npm run check` を継続的に通しながら進め、現時点では:

- `0 errors`
- `0 warnings`

のクリーン状態を達成している。

---

## このフェーズで得られた状態

現状の app モジュールは、少なくとも開始時点と比べて以下の点で大きく改善している。

- どこに何があるか追いやすい
- グローバル store の影響範囲が小さくなった
- 命名の揺れによる読解負荷が下がった
- UI コンポーネントの役割が以前より明確になった
- リファクタ継続時の安全性が上がった

つまり、これ以降は「まず土台を直す」段階から、「構造改善を継続しながら次の品質課題へ進む」段階へ移行できる。

---

## 残課題

`0_refactor` を一区切りとしてよい一方で、今後の改善余地は残っている。

### 1. 実行系の分離はまだ途中

特に `ProgramDialog` 周辺は依然として責務が重い。

- 実行制御
- 出力状態
- worker bridge
- transaction UI
- error 表示

などが近接しており、さらなる分離余地がある。

### 2. workspace domain の整理余地

`store-workspace` と `workspace-validation` は整理されたが、  
workspace に関するロジックはまだ store ベースの module に残っており、domain/service 的な層分離はこれから進められる。

### 3. dataset / process 周辺のロジック共通化

一部 helper 化は進んだが、配列編集・条件編集・スキャン関連の責務はまだ細かく分けられる。

### 4. 起動・画面遷移責務の整理

`Entry.svelte` や起動時処理周辺には、まだライフサイクル責務が多く残っている。

### 5. テスト整備

今回のフェーズは主に構造改善に寄せたため、自動テストの追加までは本格着手していない。

---

## 次フェーズ案

次に進む場合、以下の順が自然。

### Phase A: 実行系の責務分解

対象:

- `ProgramDialog`
- worker adapter / runtime state
- channel / tx 周辺

狙い:

- 実行 UI と実行制御の分離
- runtime state の局所化
- transaction 周辺の見通し改善

### Phase B: workspace/domain の整理

対象:

- `store-workspace`
- `workspace-validation`
- file load/save 周辺

狙い:

- store module と domain logic の分離
- selector / mutation / validation の整理

### Phase C: テストと回帰安全性の強化

対象:

- util
- validation
- dataset choose/scan
- workspace 操作

狙い:

- 今後の構造改善時の安心材料を作る

## まとめ

`0_refactor` は、アプリモジュールの品質改善に向けた初期整地フェーズとして十分な成果を出せた。  
命名、store、画面構成、dataset 周辺、maintenance 周辺の整理により、次フェーズへ進めるだけの土台は整っている。

以降は、`0_refactor` の続きとして細かな修正を積み増すよりも、  
次のフェーズ名を切って、実行系や domain 分離に進むほうが整理しやすい。
