# ディレクトリ責務マップ

## 目的

`app` 配下のファイル配置について、

- どのディレクトリが何を担当しているか
- どこに責務の重なりがあるか
- 今後どの方向へ整理するか

を明文化する。


## 現状の大分類

## `app/src`

フロントエンド本体。
Svelte / TypeScript による画面、状態管理、ランタイム注入、Tauri 呼び出しを持つ。

### `app/src/app`

アプリ本体。

- `Entry.svelte`
  アプリ入口
- `global.ts`
  グローバル参照
- `contents`
  画面コンポーネント群
- `store`
  アプリ状態
- `util`
  共通部品、共通ロジック


## `app/src-tauri/src`

Rust 側の Tauri バックエンド。

- file system
- scan
- process
- parser
- network scraper
- runtime state
- stream buffer

を担当する。


## フロント側責務マップ

## `app/src/app/contents`

画面コンポーネント群。
現状は以下の3区分になっている。

### `system`

アプリ全体のフレーム、メニュー、開始画面、左ツリー管理。

主な責務:

- アプリヘッダ
- ワークスペース開始 / 閉鎖
- モジュール一覧表示
- 要素追加導線

主なファイル:

- `SystemMenu.svelte`
- `MainFrame.svelte`
- `ModuleManage.svelte`
- `StartFrame.svelte`

評価:

- 役割は比較的わかりやすい
- ただし `ModuleManage` は UI に加えて要素生成ロジックも持っている


### `maintenance`

ワークスペース要素の編集画面群。

主な責務:

- env 編集
- resource 編集
- dataset 編集
- process 編集
- work 編集

主なファイル:

- `MDEnv.svelte`
- `MDResourece.svelte`
- `MDProcess.svelte`
- `dataset/MDDataset.svelte`
- `work/MDWork.svelte`

評価:

- 「右ペインで対象要素を編集する責務」にまとまっている
- 一方で naming の揺れが強い
- dataset や work はさらにサブ責務を多く抱えている


### `detail`

モーダル / ダイアログ系、および実行系 UI。

主な責務:

- program dialog
- declare dialog
- setting dialog
- transaction dialog
- output panel

主なファイル:

- `DialogManager.svelte`
- `program/ui/ProgramDialog.svelte`
- `declare/DeclareDialog.svelte`
- `setting/SettingDialog.svelte`

評価:

- 「詳細ダイアログ」という意図は読める
- ただし `detail/program` は実質的に 1 つのサブシステムになっており、単なる detail の一部としては重い


## `app/src/app/contents/detail/program`

実行系サブシステム。
現状のアプリで最も責務が集中している領域。

### `ui`

表示と操作を担う UI 層。

主な責務:

- エディタ表示
- Run / Cancel 操作
- 実行フェーズ表示
- runtime error 表示
- transaction dialog 表示

評価:

- `ProgramDialog.svelte` に責務が集まりすぎている
- 表示責務と制御責務の分離が必要


### `runtime`

Worker 実行に関するランタイム制御。

主な責務:

- Worker 実行本体
- stream flush 制御
- runtime cache

評価:

- 実行基盤として自然な配置
- ただし UI との境界がまだ薄い


### `output`

出力結果表示。

主な責務:

- text stream 表示
- table stream 表示
- channel 切り替え

評価:

- 比較的責務が明確
- 表示系として独立しやすい


### `util`

実行用の API 注入、宣言生成、Worker 呼び出し補助。

主な責務:

- `$fs`, `$net`, `$state`, `$parser`, `$channel` の注入
- monaco 用 declare 生成
- context 注入データの組み立て
- Worker invoke 補助

評価:

- util というより runtime domain / bridge に近い
- 責務が多く、後で層分割が必要


## `app/src/app/store`

状態管理。

主な責務:

- workspace 本体
- env/resource/dataset/process/work モデル
- dirty / invalidate / cache
- setting / license
- UI 状態の一部

評価:

- 現状は「ドメイン状態」と「UI状態」が混在している
- `store.ts` に集約されすぎている


## `app/src/app/util`

全体共通の補助機能。

現状含まれるもの:

- ボタン部品
- レイアウト部品
- Monaco ラッパー
- フォーム部品
- Toast
- データ変換
- パス / バリデーション
- 一部 Rust 呼び出し補助

評価:

- 共通 UI 部品置き場としては妥当
- ただし data / rust / monaco が同列に置かれており、責務粒度は粗い


## Rust 側責務マップ

Tauri command 登録の集約点。

責務:

- command の公開
- plugin 登録
- app state 管理
- drag & drop イベント連携


## `file_system.rs`

責務:

- ファイル存在確認
- text / binary 読込
- stat
- save
- rename
- copy
- mkdir
- delete

評価:

- かなり明確
- command 群としてまとまりが良い


## `scan.rs`

責務:

- dataset 用ディレクトリ走査
- include / exclude 条件適用

評価:

## `process.rs`

責務:

- 外部プログラム実行

評価:

## `runtime.rs`

責務:

- Worker ごとの Rust 側状態管理
- DOM ストア
- channel ストア

評価:

- 実行コンテキストの保管場所として自然
- 今後 worker id の扱い改善が必要


## `stream`

責務:

- channel buffer
- line buffer

評価:

- 出力ストリーム責務として明確


## `parser`

責務:

- XML / HTML パース
- DOM クエリ
- Excel 読込

評価:

- パーサ責務としてまとまっている
- API の粒度も比較的自然


## `scraper`

責務:

- HTTP / HTML 取得
- ドメインごとのアクセス制御
- response 制限

評価:

- network access 層として責務が明確


## 現状の責務重複 / 曖昧ポイント

## 1. `contents/detail/program/util` と `app/util`

問題:

- どちらにも utility があり、境界が曖昧
- 共通 util なのか、実行系専用 util なのかが名前でわかりにくい

改善方向:

- 実行系専用は `program/runtime` か `program/domain` 側へ寄せる
- 全体共通だけを `app/util` に残す


## 2. `store` と `contents/system`

問題:

- state と UI 操作が近接しすぎている
- 追加 / 削除 / バリデーションの責務が UI 側に寄っている

改善方向:

- workspace 操作用 service / action 層を作る


## 3. `detail/program/ui` と `detail/program/runtime`

問題:

- UI が実行制御まで持っている
- runtime のイベント解釈も UI に混ざっている

改善方向:

- execution controller を分離する


## 4. `src-tauri/lib.rs` への command 集中

問題:

- 公開口としては良いが、対応関係がコード上で追いづらい

改善方向:

- command 対応表を別資料で管理する


## 今後の整理方針

## フロント側

将来的には以下のように責務を読み替えるのが望ましい。

- `ui`
  表示とユーザー操作
- `domain`
  workspace / runtime のビジネスルール
- `application`
  実行制御、ユースケース
- `infrastructure`
  Tauri invoke、worker bridge、ファイル入出力


## Rust 側

Rust 側は大きくは崩れていないため、
当面は以下を優先する。

- command 境界の見える化
- request / response 型の明確化
- worker state の識別子管理改善


## 現時点の結論

現行構造は、

- 画面編集系
- 実行系
- Rust backend

の3層に大きく分かれており、完全に無秩序ではない。

一方で問題は、

- `program` サブシステムの肥大化
- `store` の責務集中
- `util` の多機能化

に集中している。

そのため、後続フェーズではまず

1. store 分割
2. ProgramDialog 周辺分割
3. util 再配置

の順で進めるのが妥当である。
