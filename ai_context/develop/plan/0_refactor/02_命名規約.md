# 命名規約

## 目的

アプリモジュール内の命名を統一し、

- どこに何があるか探しやすくする
- 新規実装時の判断コストを減らす
- 名前から責務やレイヤーを推測しやすくする

ことを目的とする。


## 基本方針

## 1. ファイル名は見た目で種類が分かるようにする

- `.svelte` は UI コンポーネントなので `PascalCase`
- `.ts` はモジュールとして扱い、`kebab-case`
- Rust は言語標準に合わせて `snake_case`


## 2. ファイル名と export 名の役割を揃える

- ファイル名はモジュールの責務を表す
- export 名はコード上での概念名を表す
- ファイル名と export 名が完全一致しなくてもよいが、意味は一致させる


## 3. 略語はできるだけ減らす

特に以下の層では略語を避ける。

- 画面コンポーネント
- store
- service
- controller
- bridge

補足:

- スコープが狭い内部実装では `tx` などを限定的に許容してよい
- ただし新規追加では、原則として完全語を優先する


## 4. typo は放置しない

- typo は設計判断ではなくノイズなので、見つけ次第直す方針とする


## 採用する命名規則

## `.svelte` ファイル

### 規則

- `PascalCase.svelte`

### 例

- `ProgramDialog.svelte`
- `SystemMenu.svelte`
- `TextStreamView.svelte`

### 理由

- Svelte コンポーネントは JSX / Svelte テンプレート上で型のように扱うため、`PascalCase` が最も自然


## `.ts` ファイル

### 規則

- `kebab-case.ts`

### 例

- `workspace-store.ts`
- `context-data-util.ts`
- `worker-adapter.ts`
- `program-execution-controller.ts`

### 理由

- `StoreX.ts` と `storeX.ts` のような揺れを防げる
- 単語境界が視認しやすい
- ディレクトリ一覧で均一に見える
- export 名とファイル名の役割を分けやすい


## `.rs` ファイル

### 規則

- `snake_case.rs`

### 例

- `file_system.rs`
- `line_buffer.rs`

### 理由

- Rust の一般的な規約に従う


## 役割ごとの命名ルール

## コンポーネント

### ルール

- UI コンポーネントは名詞ベース
- 何を表示するかを名前に出す

### 例

- `ProgramDialog`
- `ProgressBar`
- `ChannelSwitchFrame`

### 避けたい例

- `MDWork`
- `PRDataset`

理由:

- 略語前提で役割が分かりにくい


## Store

### ルール

- store を表すファイルは `*-store.ts`
- export 名は `xxxStore` もしくは `createXxxStore`

### 例

- `workspace-store.ts`
- `ui-store.ts`
- `app-store.ts`
- `runtime-store.ts`

### 補足

- 単なる型定義だけなら `*-model.ts` や `types.ts` を使う
- state 本体と model 定義を混ぜない


## Service / Controller / Bridge

### ルール

- 役割を接尾辞で明示する

### 例

- `workspace-service.ts`
- `program-execution-controller.ts`
- `runtime-bridge.ts`
- `transaction-bridge.ts`

### 理由

- util より責務が明確になる


## Util

### ルール

- 本当に汎用なものだけ `*-util.ts`
- 役割が明確なら `util` ではなく責務名を使う

### 良い例

- `path-util.ts`
- `validate-util.ts`

### 避けたい例

- `data-util.ts`
- `file-util.ts`

理由:

- 責務が広がりやすい


## Type / Model

### ルール

- 型が主目的なら `types.ts` または `*-types.ts`
- ドメインモデルなら `*-model.ts`

### 例

- `workspace-types.ts`
- `process-model.ts`


## イベント / Factory / Builder

### ルール

- 何を作るかを名前に含める

### 例

- `worker-event-factory.ts`
- `declare-builder.ts`
- `context-projection-builder.ts`


## 略語ポリシー

## 原則として避ける略語

- `MD`
- `PR`
- `dcl`
- `mgr`
- `cfg`

理由:

- プロジェクト固有文脈がないと意味が分からないため


## 条件付きで許容する略語

- `tx`
- `fs`
- `ui`
- `api`

条件:

- 業界標準レベルで意味が共有されている
- スコープが狭い
- 完全語にするとかえって冗長すぎる

ただし、公開層では完全語を優先してよい。

例:

- `transaction-dialog` はよい
- `tx-plan-util` は内部 util なら許容余地あり


## export 名のルール

## namespace は新規では増やさない

### 方針

- 新規 `.ts` では `namespace` を基本採用しない
- `function`, `const`, `class`, `type` の通常 export を使う

### 理由

- モジュール境界が分かりにくくなる
- 責務分割後に再利用しづらい


## export 名

### ルール

- 関数は `camelCase`
- 型 / クラス / コンポーネントは `PascalCase`
- 定数は `UPPER_SNAKE_CASE` または `camelCase`


## 一律ケバブケースの是非

## 結論

`.ts` ファイルを一律 `kebab-case` にするのは、かなり有力であり、採用してよい。

むしろ現行の課題を考えると、

- `StoreX.ts`
- `storeX.ts`
- `xxxUtil.ts`

の混在を止めるために効果が大きい。


## 採用メリット

- 命名揺れを止めやすい
- ディレクトリ一覧で見やすい
- 単語区切りが明確
- export 名との役割分離がしやすい
- React / Svelte 以外の TS モジュールでも統一しやすい


## 注意点

### 1. `.svelte` まで一律ケバブケースにはしない

理由:

- コンポーネントは `PascalCase` が自然
- テンプレート上で型的に見えるため


### 2. ファイル名だけ変えて責務を曖昧にしない

例:

- `file-util.ts`

のような名前をケバブケース化しても、本質的に責務が曖昧なら改善は弱い。


### 3. export 名は別で整理する

ファイル名が `context-data-util.ts` でも、
中の export が曖昧なら効果は限定的である。


## 推奨方針

### 採用案

- `.svelte`: `PascalCase`
- `.ts`: `kebab-case`
- `.rs`: `snake_case`

この方針を採用するのが最も整理しやすい。


## 既存コードへの適用方針

## すぐ直す対象

- typo
- 明らかな大文字小文字揺れ

例:

- `toastUtit.ts`
- `storeLIcense.ts`


## 構造改善とセットで直す対象

- `fileUtil.ts`
- `dataUtil.ts`
- `declareUtil.ts`
- `contextDataUtil.ts`
- `workerAdapter.ts`

理由:

- 単純改名より、責務分割後に適切な名前へ変える方が価値が高い


## 保留してもよい対象

- `tx` 系の内部 util

理由:

- スコープが限定されており、優先度は比較的低い


## 新規作成時のルール

新規ファイルはこの規約を先行適用する。

### 例

- `program-execution-controller.ts`
- `program-context-resolver.ts`
- `runtime-bridge.ts`
- `workspace-validation-store.ts`


## 現時点の結論

大きな方針として、`.ts` ファイルを一律ケバブケースにするのは十分ありであり、
現行資産の改善にも相性がよい。

今回のプロジェクトでは、以下を採用方針とする。

- `.svelte` は `PascalCase`
- `.ts` は `kebab-case`
- `.rs` は `snake_case`

このルールを基準に、後続フェーズで命名統一を進める。
