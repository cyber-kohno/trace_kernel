# V8採用とホスト基盤の整備

2026-10-13。ユーザーの「V8採用で進めてください」により、製品CLIのJavaScriptエンジンはV8に決定した。28の比較結果は実施時点の履歴として残す。本資料以降は採用判断を再度求めない。

## V8ホストの整備

`experiments/js-host-v8`の依存をCargo.lockで固定し、deno_core 0.412.0にdeno_web 0.290.0とdeno_webidl 0.259.0を追加した。製品CLI入口はまだ追加していない。

- Denoの実装からURL/URLSearchParams、TextEncoder/TextDecoder、DOMException、structuredClone、setTimeout/setIntervalを導入した。
- structuredCloneはtransferオプションを受け付けるmessage_port側の実装を使い、単一isolate内の転送にも必要なbacking-store tableをRuntimeOptionsへ設定する。
- V8比較にQuickJS用の簡易profile.jsを重ねない。V8の実際のAPIで同じWork/context/Logic/出力scheduler/transactionを実行する。
- Work完了時に、残っているユーザータイマーを解除してから出力完了とtransactionへ進む。Workがawaitしているタイマーは実行中に動作する。
- 期限・cancel・near-heap-limit callbackによる停止は従来どおり維持する。
- 別スレッドから5ms間隔でV8へinterruptを要求し、ヒープ統計の取得自体はisolateの実行スレッドで行う。未実行のinterruptを重複登録しない。
- used_heap_sizeとexternal_memoryの合計を検査する。native呼び出し、timer callback、Work完了、最終結果変換にも検査地点を置く。超過時はisolateを停止し、JavaScriptのcatchで継続してtransactionを適用できないようにする。
- interrupt callbackはisolateのslotが所有するArcを参照する。watchdogからRustの一時領域への生ポインタを渡さない。

## 保証範囲

上限超過は検査時に停止する。単一の配列/ArrayBuffer確保が一時的に設定値を超えることはある。RSS、Rust側の全確保、単一builtin中のピークメモリの厳密な上限ではない。near-heap-limit callbackには停止を観測するための128MiBの一時猶予がある。32MiBを超える確保が一切起きないという意味で扱わない。

Web APIは代表的な挙動を試験する。ブラウザとの完全互換、任意コードに対するsecurity sandbox、クリーンPCでの配布確認は未実施。native I/Oは比較用のメモリモデルのままであり、実native要求の所有と停止は今後共通native-coreへ接続する。

## 検証手順

```powershell
cargo build --release --locked --manifest-path experiments/js-host-v8/Cargo.toml
node experiments/js-host-v8/compare.mjs --release
node experiments/js-host-v8/verify-host.mjs
cargo clippy --locked --manifest-path experiments/js-host-v8/Cargo.toml --all-targets -- -D warnings
```

比較はWork結果19件、停止5件、資源・失敗4件、コンパイラ2件。前回差分として記録した単発配列確保も、今回は停止を必須条件にした。追加試験はURLの重複パラメータ、日本語URL、decoderのstream/fatal/Shift-JIS、cloneの循環/Map/Date/transfer/不許可値、interval引数/解除、await済みtimerと背景timerの解放、配列/ArrayBufferとCPU/microtask中の超過、catch後のtransaction適用防止を対象とする。

最終バイナリで両エンジンの比較30件ずつと、V8追加試験12件が成功した。V8 releaseビルドとClippy全target（警告をエラー扱い）も成功。追加試験は`--bootstrap-source`を使わず、exeに組み込んだbootstrapで通過した。timer callback失敗時と、実際の共通Work入口による背景timer解除も確認した。

今回のV8 exeは60,746,240 bytes（約57.93MiB）、最小プロセス10回の中央値約81.3ms、コンパイラ初期化と1行変換約468ms、Work出力まで約493ms。共通Workバンドル525,890 bytes。28とAPI構成が変わり、計測値にはその影響と実行時の負荷を含む。大規模Workの性能やピークRSSを示す値ではない。
