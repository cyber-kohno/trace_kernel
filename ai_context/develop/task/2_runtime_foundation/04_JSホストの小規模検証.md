# JSホストの小規模検証

2026-10-12。共通化方針の第3段階。

## 判断

別Rust CLIで、既存TypeScriptの実行API・VFS・トランザクションサービスを使う構成は、小規模検証では成立した。
TypeScriptの変換もDesktopと同じコンパイラをRustホスト内で実行できた。
CLIのためにVFSやトランザクションの判断をRustへ二重実装する必要はない見込み。

ただしQuickJSを製品の採用エンジンとして確定したわけではない。
Windows/MSVC、ブラウザとの互換性、コンパイラのコスト、実際のWork全体の受入試験を確認してから決める。
apps/cli、packages/runtime-core、crates/native-coreはまだ作成・移動していない。

## 候補と今回の範囲

| 候補 | 今回の扱い |
| --- | --- |
| rquickjs / QuickJS-NG | RustのFutureとPromiseを接続できるため、まず実装・実測した。Windows/MSVCは公式の対応表で実験的扱い。今回の環境ではビルド・実行できたが、配布対象全体の保証ではない。[公式情報](https://github.com/DelSkayn/rquickjs#supported-platforms)、[非同期API](https://docs.rs/rquickjs/0.14.0/rquickjs/struct.AsyncRuntime.html) |
| deno_core / V8 | 別候補として残す。rusty_v8は通常、ビルド時に事前ビルド済みライブラリを取得する。ビルド資産・配布サイズの比較は未実測。[公式情報](https://github.com/denoland/rusty_v8#binary-build) |
| Boa | Rust製の候補。ただし公式でもexperimentalとしている。今回のケースでの互換性・非同期処理・停止は未検証。[公式情報](https://github.com/boa-dev/boa#boa) |

「他候補より優れている」ことを比較測定したのではなく、独立Rustホストで共通コードを動かす際の必要条件を調べた。

## 実験の配置

```text
experiments/js-host-quickjs/
  Cargo.toml / Cargo.lock   製品と独立したworkspace、固定した依存
  src/main.rs               Rustホスト、非同期境界、期限・停止、メモリ上のI/O
  fixture.ts                既存API・VFS・サービスを使用する実行器
  compiler-fixture.ts       Desktopと同じTypeScript変換
  host-call.ts              WorkerInvokeの代わりの境界
  profile.js                検証に必要な最小の文字コード・タイマー機能
  cases.mjs                 同じ入力で比較するケース
  compare.mjs               バンドル生成、Node/V8比較、停止試験、計測
  generated/                再生成可能な出力。Git対象外
```

- Desktopの依存・本体コードはこの段階では変更していない。
- RustのI/Oはメモリ上のモデル。実ファイルの保存・削除は行わない。
- 出力はJSON報告のstdoutフィールドへ保存する。製品CLIの直接ストリーミングは未実装。
- Nodeはバンドル生成と比較に使用。Rustホスト自体はNode・Tauri・WebViewを起動しない。
- 既存のWorkerInvokeのみをバンドル生成時に差し替え、API・VFS・サービスのコードは複製しない。
- 出力注入・完了待ち・I/Oアダプターは実験用。現行Workerのライフサイクルをそのまま移植したものではない。

## 検証結果

実行環境はRust 1.90.0、x86_64-pc-windows-msvc、Node v22.18.0、rquickjs 0.14.0。
releaseビルドを使用した。

| 区分 | 件数 | 確認内容 |
| --- | --- | --- |
| Node/V8との比較 | 11 | 非同期出力、return、exit、7種類のトランザクション操作、Shift_JIS、実行例外、I/Oの拒否、競合、部分適用失敗、JSON/CSV、Map/Set/TypedArray/BigInt |
| 停止 | 5 | CPU無限ループ、無限microtask、未解決Promise、タイマー待ちの期限超過、別スレッドからのキャンセル |
| 資源・失敗 | 3 | JSヒープ上限、スタック上限、出力失敗後にコミットしないこと |
| ホスト内TypeScript変換 | 2 | Desktopと同じoutputText/sourceMapText等の一致、変換後のワーク実行・出力 |

21ケースが成功。Node/V8比較では出力・ホスト呼び出し・操作結果・最終的なメモリ上のファイル状態まで照合した。
ただしNode VMは実際のブラウザWorkerではなく、DesktopのGUI経路全体の互換性試験ではない。

- 全件検証の失敗やワーク実行の失敗では、staged transactionを適用しない。
- 部分適用失敗は成功1件・失敗1件・未実行1件を区別し、後続に進まない。
- 出力の完了待ちはトランザクション適用の前に行う。出力の失敗時には適用しない。
- 停止試験はユーザーコードの実行開始を別途記録し、初期化中に停止しただけの結果を合格にしない。
- 最終実行では、300msの期限超過ケースは約301-316ms、実行開始後30msで要求したキャンセルは初期化を含め約62msで終了した。
- JavaScript内のCPUループにはエンジンのinterrupt、待機中にはホストの期限を併用する必要がある。
- CLI側で未解決Promiseも終了判断の対象にする必要がある。

追加で、cargo clippy --all-targets -- -D warningsとDesktopのnpm run checkが成功。
DesktopのSvelteエラー・警告は0件、トランザクションテスト37件も成功。

## コストの実測

| 対象 | 今回の値 | 注意 |
| --- | --- | --- |
| 検証用Rust exe | 1,380,352 bytes、約1.32MiB | JS資産・本製品のnative機能を含まない |
| API/VFS等のJSバンドル | 508,495 bytes、約0.49MiB | 検証用実行器。未圧縮 |
| TypeScriptコンパイラバンドル | 10,149,996 bytes、約9.68MiB | 未圧縮。現状は入力で渡し、exeには埋め込んでいない |
| 最小プロセス起動の中央値 | 約25.9ms | 同じPCで10回。アプリの起動時間・コールド起動ではない |
| コンパイラ初期化と1行の変換 | 約682ms | Rustホスト内。プロセス起動・stdin読込を除く |
| コンパイラ初期化からワーク出力まで | 約737ms | 小さな1ケース。大規模コードのベンチマークではない |
| 変換試験のJSヒープ上限 | 128MiB | 設定値であり、実使用量・ピークRSSの測定値ではない |

Rust exeだけのサイズからCLI全体の軽さを判断してはいけない。
コンパイラと共有JS資産の埋め込み・圧縮・初期化方式を含めて配布コストを評価する。
現行TypeScriptコンパイラを維持すれば変換規則の二重実装を避けられるが、そのコストは無視できない。

dumpbin /dependentsではVCRUNTIME140.dllとWindows/UCRT系の依存を確認した。
WebViewやNodeのDLLはリストにないが、クリーンな配布先PCでの動作は未検証。
CRTをどう配布・リンクするかも製品化前に判断する。

## 残る判断材料

- QuickJSにはTextEncoder/TextDecoder、setTimeout、URL等が標準ではない。今回、必要な文字コード・タイマーだけを補った。完全なWeb API互換性を主張するものではない。
- 新しい標準機能、Intl、Date/タイムゾーン、正規表現、TextDecoderの詳細なオプション、背景タスクは未検証。ユーザーが使ってよいグローバルの契約を固定する必要がある。
- .trk読込、Work/Logic/Declareの依存解決、事前の意味的な型検証、ライセンス判定は未実装。TypeScriptのtranspile成功は型検証成功とは異なる。
- XML/HTML/Excel、ネットワーク、外部プロセス、実ファイルI/Oを含むWork全体は未検証。現状のメモリI/O比較はOS操作の安全性を証明しない。
- エラースタックの生データは保持できたが、TypeScriptソースへの行番号変換・GUIエラー表示の同等性は未検証。
- 今回の完了待ちは実験用の明示的な出力キュー。現行stream-flushの完了保証、未awaitの処理、unhandled rejection、タイマーの寿命、cancel/disposeの整備はまだ必要。
- JSヒープの上限はRust側のJSON・バイナリ等のメモリを制限しない。大量データ・長時間処理・安全なホスト境界の検証は別途必要。
- Windows/MSVCの継続的なビルド・更新、実際の配布先PC、その他OS、依存の更新・通知事項は採用前の確認項目。
- 原子的更新、競合の完全防止、ロールバックは今回も追加していない。

## 次に進めること

エンジン固有の製品実装には進まず、合意済みの第4段階へ進める。
まず現行Workerの出力完了・準備失敗・実行終了の契約を固定し、cancel/disposeとUIの寿命から切り離してテストを追加する。
その後、Workspaceの読込・検証・実行準備を抽出し、代表Workを複数のホストで比較できる段階でエンジンを最終判断する。
