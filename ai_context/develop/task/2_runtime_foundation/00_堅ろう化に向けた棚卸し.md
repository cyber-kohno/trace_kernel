# CLI化に先立つ実行基盤の棚卸し

調査日: 2026-10-12。対象: `apps/desktop`。調査時のHEAD: `3a9fd63`。

## 前提と調査範囲

GUIで作成したワークを将来CLIでも実行できるようにするため、まず現在のGUI製品の安全性と保守性を整える。
今回の成果物は棚卸しと着手順序であり、アプリの実装変更は行っていない。
既存の `src-tauri/Cargo.toml` の変更には手を加えていない。

調査対象は実行、Worker通信、出力、トランザクション、ワークスペース読込・検証、RustのI/O境界、関連テスト。
既存の `0_refactor` の成果を引き継ぐ。ストア分割、命名整理、APIの回帰テストは既に存在する。
全画面・全APIの網羅監査、実ファイルを使った破壊的操作の試験、GUI操作による再現は今回の範囲に含まない。

証拠の区分:

- **再現確認**: 現行TypeScriptをトランスパイルして読み込み、I/Oをモックに置換した診断で再現。
- **コード確認**: 呼出経路や条件分岐から確認。実GUI・OS上の障害試験は未実施。
- **設計課題**: 製品として必要な保証や責務境界がまだ定まっていない。

## A: トランザクション

### A1. ディレクトリ削除が作成命令に変換される [再現確認]

`deleteDir()` は `dirTable` に `intent: 'delete'` を記録するが、正規化はintentを見ず全件を `create_dir` にする。
`Order` とExecutorにもディレクトリ削除の命令がない。
削除予定のディレクトリが存在すれば検証が通り、作成の冪等処理として成功扱いになり得る。

根拠: [tx-plan-normalize.ts:56](D:/app/git/trace_kernel/apps/desktop/src/app/contents/detail/program/ui/tx/util/tx-plan-normalize.ts:56)、`util/fs/tx/delete-dir.ts`。
診断結果: `intent: 'delete'` を入力すると `[{ type: 'create_dir', path: ... }]` が返る。
最初のテスト: 全公開トランザクション操作が正しい命令に変換されること。削除の空ディレクトリ・非空ディレクトリの契約も固定する。

### A2. ファイル削除のTauriコマンドが不一致 [再現確認・コード確認]

`TxCommitRunner.deleteFile()` は `delete_path` を呼ぶ。Rustが登録しているのは `delete_file` で、`delete_path` は未登録。
VFS上のAPI試験では通っても、実際のコミット経路では削除できない。

根拠: [tx-commit-runner.ts:28](D:/app/git/trace_kernel/apps/desktop/src/app/contents/detail/program/ui/tx/util/tx-commit-runner.ts:28)、[lib.rs:100](D:/app/git/trace_kernel/apps/desktop/src-tauri/src/lib.rs:100)。
診断結果: 呼ばれたコマンドは `delete_path`。
最初のテスト: TSの削除操作とRustの公開コマンドの対応を確認し、一時ディレクトリで削除まで通す結合テスト。

### A3. renameの検証が実際と異なるパスを確認する [再現確認]

Executorは絶対パスである `order.to` を渡すが、検証側は「新しいファイル名」と解釈し、元のディレクトリを再度付加する。
実際の宛先に対する存在チェックが行われない。

根拠: [tx-executor.ts:79](D:/app/git/trace_kernel/apps/desktop/src/app/contents/detail/program/ui/tx/util/tx-executor.ts:79)、[tx-verify-util.ts:223](D:/app/git/trace_kernel/apps/desktop/src/app/contents/detail/program/ui/tx/util/tx-verify-util.ts:223)。
診断結果: `C:\fixture\new.txt` の代わりに `C:\fixture\C:\fixture\new.txt` を確認する。
最初のテスト: 既存の宛先、同名、正常renameについて、検証と適用が同じパスを使うこと。

### A4. コミット途中の失敗後も後続操作を続ける [再現確認]

各命令の `status.commit` がerrorでもループを続行する。全体の結果は戻り値として返らない。
失敗した命令を前提とする後続操作も実行され、部分的な更新の範囲が広がる可能性がある。

根拠: [tx-executor.ts:96](D:/app/git/trace_kernel/apps/desktop/src/app/contents/detail/program/ui/tx/util/tx-executor.ts:96)。
診断結果: 最初の保存をerrorにしても、次の保存が呼ばれる。runの戻り値はundefined。
最初のテスト: 途中失敗時の停止、実行済み・失敗・未実行の識別、全体が成功扱いにならないこと。

### A5. 読込時のsnapshotが変更競合の検証に使われない [コード確認]

`openText()` はmtimeとsizeを取得し、正規化後のmodify命令にもsnapshotを残す。
しかしmodifyの検証は存在・ファイル種別・readonlyのみで、snapshotやoriginalとの比較がない。
読込後に外部で変更されたファイルを上書きする可能性がある。

根拠: [tx-plan-normalize.ts:93](D:/app/git/trace_kernel/apps/desktop/src/app/contents/detail/program/ui/tx/util/tx-plan-normalize.ts:93)、[tx-executor.ts:72](D:/app/git/trace_kernel/apps/desktop/src/app/contents/detail/program/ui/tx/util/tx-executor.ts:72)。
最初のテスト: 読込後の外部変更を検出して更新を拒否すること。size/mtimeだけでよいか、内容比較も必要かを決める。

### A6. 「トランザクション」が保証する範囲を固定する [設計課題・コード確認]

現行は「VFSに蓄積し、全件を事前検証してから順番に適用する」方式。
今回追った適用経路には、複数ファイルの一括原子性、ロールバック、永続的な適用記録は見当たらない。
Rustの保存は `fs::write` であり、単一ファイルも一時ファイル経由の置換にはなっていない。
また `$fs.saveText/deleteFile` 等の直接更新と `$process` の外部処理はVFSの対象外。

根拠: [file_system.rs:235](D:/app/git/trace_kernel/apps/desktop/src-tauri/src/file_system.rs:235)、`util/fs/dcl-file-system.ts`。
決めること: 事前検証、競合検出、途中失敗時の停止、単一ファイルの保存保証、復旧方法、対象外の副作用。
複数ファイルを完全に原子的に更新する保証が必要なら、別途設計する。抽象化だけではその保証は増えない。
現行はwarningも1件あればコミットしない。「エラー0なら確定」というCLI要望との違いは、仕様として解決する必要がある。
最初のテスト: 検証エラー・warningがあると更新0件、競合検出、保存失敗、部分適用の結果。保証拡張後は中断・復旧試験。

## B: 実行の寿命と出力

### B1. 実行準備の失敗が終了通知にならない [再現確認]

Workerのtry/catchはユーザーコードの実行部分だけを囲む。
datasetスキャン、worker_init、コンテキスト生成、Function生成は外側で、失敗するとruntime-error/doneが出ない。
AdapterにもWorkerのerror/messageerrorを終了結果へ変換する処理がない。
GUI側のsnapshot保存やtranspileの失敗も、phaseをpreparingにした後の例外経路が未整理。

根拠: [worker.ts:112](D:/app/git/trace_kernel/apps/desktop/src/app/contents/detail/program/runtime/worker.ts:112)、[worker.ts:178](D:/app/git/trace_kernel/apps/desktop/src/app/contents/detail/program/runtime/worker.ts:178)、[ProgramDialog.svelte:211](D:/app/git/trace_kernel/apps/desktop/src/app/contents/detail/program/ui/ProgramDialog.svelte:211)。
診断結果: スキャンをrejectするとハンドラがrejectするだけで、終了イベントは0件。
目標: 準備・ユーザーコード・出力の各段階で失敗しても、型付きの終了結果を1回返すExecutionSession。
最初のテスト: 準備失敗、ユーザー例外、文字列/nullのthrow、Worker起動失敗、キャンセル、通常return、runtime.exit。

### B2. 画面破棄と資源解放が結び付いていない [コード確認]

ProgramDialogのonDestroyはUI状態とMCP提案の処理のみで、WorkerのterminateやRust実行contextのdisposeを呼ばない。
Escapeでダイアログが破棄された場合、Workerや進行中のI/Oが残る経路がある。
成功後の出力閲覧のための保持と、画面破棄後の解放を区別した所有権が必要。

根拠: [ProgramDialog.svelte:92](D:/app/git/trace_kernel/apps/desktop/src/app/contents/detail/program/ui/ProgramDialog.svelte:92)、[worker-adapter.ts:57](D:/app/git/trace_kernel/apps/desktop/src/app/contents/detail/program/ui/worker-adapter.ts:57)。
目標: cancel/disposeの冪等性、旧実行の遅延応答の無視、Worker・Rust context・出力保持の寿命を明示。
最初のテスト: 実行中の画面閉鎖、連続実行、二重停止、停止後のI/O応答、閲覧終了後のcontext解放。

### B3. 出力を保存し終える前にdoneが通知される [再現確認]

FlushSchedulerにはscheduleだけがあり、完了をawaitする口がない。Workerはユーザー関数の終了だけでdoneを出す。
診断結果の順序: `append_started -> done -> append_completed -> receive_stream`。
CLIでdoneをもとにプロセスを終了すると末尾の出力を失う可能性がある。
キューは送信前にspliceされ、送信失敗の回復・全体への伝播も未整理。
Rustのadd_channel/append_linesも内部Resultを捨てている。

根拠: [worker.ts:197](D:/app/git/trace_kernel/apps/desktop/src/app/contents/detail/program/runtime/worker.ts:197)、`runtime/stream-flush.ts`、`src-tauri/src/stream/channel.rs`。
目標: UI表示に依存しないOutputSink。出力の登録・順序・drain・失敗を管理し、その完了後に終了を確定。
最初のテスト: 最後の1行、複数channel、flush中の追加、登録失敗、保存失敗、大量出力時の上限・流量制御。

## C: ワークスペースと外部I/O

根拠: [file-util.ts:141](D:/app/git/trace_kernel/apps/desktop/src/app/util/data/file-util.ts:141)、`service/validation-service.ts`、`mcp/semantic-work-validator.ts`。

### C2. エラーと正常値の境界が曖昧 [コード確認]

Rustのread_fileは読込エラーをStringに変えて正常応答する。
dataset.content()等ではエラーメッセージがファイル内容として処理され得る。
command名はstring、引数はanyで、A2のような不一致を型チェックでは検出できない。

根拠: [file_system.rs:84](D:/app/git/trace_kernel/apps/desktop/src-tauri/src/file_system.rs:84)、`util/worker-invoke.ts`。
目標: 型付きrequest/response、正常値とResultの分離、実行IDを伴うI/O境界。I/O先をモックへ差し替え可能にする。
最初のテスト: ファイル不在、読込拒否、未登録command、DTO不一致、通信エラー、失敗がユーザーコードまで伝わること。

### C3. タイムアウトやcancel後に実処理が残る可能性 [コード確認]

WorkerInvokeは一律10秒で待機を打ち切るが、run_processには別のtimeout設定がある。
10秒より長い有効な処理も通信側が先に失敗し、Rust処理を止める通知は送られない。
Rustのprocess処理はkill_on_drop等を設定せず、待機のtimeoutで終了する。cancelと子プロセスの寿命を結び付けていない。
stdin書込もtimeoutで囲ったwait処理の前にある。実際の子プロセス残存はOS上の試験が必要。

根拠: [worker-invoke.ts:7](D:/app/git/trace_kernel/apps/desktop/src/app/contents/detail/program/util/worker-invoke.ts:7)、`util/context-data-util.ts:207`、`src-tauri/src/process.rs`。
目標: 実行単位で所有する外部処理、I/Oごとのtimeout、cancel要求と実処理停止の区別。
最初のテスト: 10秒超の正当な処理、timeout、stdin停止、キャンセル、子プロセス終了・回収、遅延応答。

## D/E: 責務と配置

Workerだけを分離しても、UI依存は残る。
`worker.ts -> ui/worker-adapter.ts`、`ContextDataUtil -> FileUtil -> UI/ストア`、`DeclareUtil -> LicenseState -> appStore` という実行時依存がある。
ContextDataUtilにはcontext選択・実行オブジェクト生成・宣言生成・logicコンパイルが同居する。
WorkerAdapterもWorker側送信・メイン側受信・Tauri接続を兼ねる。

目標は、実行開始時にWorkspaceの実行用snapshotと明示的なCapabilitiesを渡し、実行中にGUIのグローバル状態を参照しないこと。
型宣言と実行APIは共通規則を保ち、既存のPro/API整合テストを維持する。
最初から全API分の巨大なインターフェースを作らず、トランザクションのFileSystemPortと実行イベントから分離する。

配置案は `src/app` の既存方針を維持する:

```text
domain/              Workspace、TransactionPlan、純粋な検証・変換
service/execution/   実行準備、Session、終了結果
service/transaction/ 検証と適用の制御、結果
infra/tauri/         TauriコマンドとDTO
infra/worker/        Web Worker起動、通信
contents/            Svelte画面、表示用状態への変換
```

具体的な移動はサービス抽出とテスト追加に合わせて小さく行う。全ファイルの一括移動は初手にしない。
`maintenance/work` と `maintenance/program`、複数のMaintenanceLogic、複数のtransactionモデル等は、参照元と用途を確認して後段で整理する。
既存文書は旧構造の記述も残るため、新しい境界が定着した段階で実装マップを更新する。
共通packagesへの切出しや独立Rust crate化は、CLIの実行ホストと実際の共有範囲を確認して判断する。
ブラウザWorkerとTauri invokeをそのままNode/Rust CLIへ移せるわけではなく、JS実行環境と配布方式の小さな技術検証は別途必要。

## 推奨する着手順序と完了条件

1. **トランザクションの回帰テストと不具合修正。** A1-A4を先に再現する失敗テストを追加し修正する。続いてA5の競合検出を固定。GUIの命令表示と結果も確認する。
2. **保証範囲を文書化し、TransactionServiceを抽出。** UIのOrderRowやphase更新から独立したPlan/VerifyReport/CommitReportを返す。途中失敗・warningの扱いを明示し、一時ディレクトリで結合試験する。
3. **出力と終了の契約を実装。** drainと失敗伝播を先に作り、終了イベントを1回に揃える。OutputSinkの試験に加えRustのLineBuffer/ChannelStoreを試験する。
4. **ExecutionSessionを抽出。** ProgramDialogは開始・停止・イベント表示を担う。準備失敗、cancel、画面破棄、再実行、資源解放をGUIとモックで確認する。
5. **Workspace読込・検証・注入を独立。** GUIなしでtrkからExecutionRequestを作る。Monaco/MCPと共通の検証・宣言規則を使用し、Capabilitiesを明示する。
6. **I/O寿命と配置を仕上げる。** 外部processのtimeout/cancelを試験し、担当領域へファイルを移動。通常のcheckに単体・結合テストを組み込み、CIで実行する。
7. **CLIホストの技術検証と最小runner。** 同じサービスを使用し、成功・検証失敗・実行失敗・出力失敗・部分適用を終了コードと結果へ変換する。

CLI着手の条件は、全コードの完全な整理ではなく次の具体的な状態:

- GUIなしでWorkspaceを読込・検証し、実行要求を作れる。
- 成功・失敗・cancelが同じ契約で終わり、出力が完了してから終了する。
- トランザクションの検証・適用がUIなしで試験でき、部分適用を成功と区別できる。
- 競合、warning、直接更新・外部process等の対象外副作用の扱いが決まっている。
- 現在のGUIの主要な回帰シナリオがチェックで守られている。
