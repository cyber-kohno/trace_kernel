# V8ホスト比較とエンジン選定

**採用確定の追記:** この比較後、ユーザーの「V8採用で進めてください」によりV8採用が確定した。追加整備は[29_V8採用とホスト基盤の整備](29_V8採用とホスト基盤の整備.md)、共通crateへの移行は[30_native_coreへの初期移行](30_native_coreへの初期移行.md)を参照。以下は採用前の比較記録。

2026-10-13。ユーザーが「V8系も追加比較してから選定する」を選択したため、独立RustのV8ホストを実装し、QuickJSと同じ入力で測定した。製品CLIは未実装、採用確定はまだ行っていない。

## 実装と再現

- `experiments/js-host-v8`にdeno_core 0.412.0、V8 15.0.245.2-rustyを使用する独立したCargo workspaceを追加した。依存はCargo.lockで固定。Intlを確認するためICUデータをexeに含める設定にした。
- `experiments/js-host-common/native-model.rs`に両候補のメモリI/Oモデルを共通化した。Work/Logic/権限選択/出力schedulerのJSは27と同じfixtureを共有し、V8側は異なる実行APIへ接続する。
- V8はRustのasync opをPromiseへ接続し、別スレッドからisolateを停止する。CPU/microtaskループ、未解決Promise、native待ちを同じ期限で扱う。終了後のevent loopの完了待ちも期限付き。
- V8の停止でJS Promiseが未解決のまま残る場合は、Rustの停止原因を直接観測して戻る。memory callbackによる停止を単なる期限超過に誤分類しない。
- ビルドと比較手順はV8実験の`README.md`を参照。`node experiments/js-host-common/compare-engines.mjs`でrelease版を順に実行し、`js-host-common/generated/comparison.json`へ結果を保存する。生成物はGit管理対象外。

## 比較結果

Windows/MSVC、Rust 1.93.1、Node v24.13.1で測定した。共通Workバンドル525,800 bytes、TypeScriptコンパイラ10,149,996 bytesは両候補で一致する。

| 対象 | QuickJS | V8 |
| --- | --- | --- |
| 実験用exe | 1,370,112 bytes（約1.31MiB） | 56,521,216 bytes（約53.90MiB） |
| 最小プロセス起動の中央値（10回） | 約39.6ms | 約61.8ms |
| コンパイラ初期化と1行変換 | 約827ms | 約327ms |
| コンパイラ初期化からWork出力まで | 約827ms | 約392ms |
| Work/Logic/context/出力/権限/transaction結果 | 19件一致 | 19件一致 |
| 停止（CPU、microtask、未解決Promise、待ち、外部cancel） | 5件成功 | 5件成功 |
| ホスト内コンパイラ | 2件成功 | 2件成功 |
| Intl.NumberFormatの簡単な確認 | 未提供 | Nodeの結果と一致 |
| URL/URLSearchParams/structuredClone/setInterval | 未提供 | 未提供 |

Dateの固定UTC値、Unicode正規表現、UTF-8の簡単な挙動もNodeと一致した。完全なIntl/Web API互換性を検証したものではない。V8でも必要なWeb APIをホスト側で整備する必要がある。

全30シナリオ中、QuickJSは30件が期待した結果になった。V8は29件が期待した結果になり、単発の大きな配列確保1件は下記の差分として記録した。比較スクリプトが完了したことを、メモリ上限の保証が同等という意味で扱わない。

exeのサイズはICUを含む今回の実験構成。共通JS、コンパイラ、本製品native機能は含まない。コンパイラ計測は単発で、最小起動もキャッシュ状態やウイルス対策等の影響を含む。この値から大規模Workの性能を判断しない。

## メモリの差

- 共通の「配列12,000,000要素を一度に確保する」入力をQuickJSは拒否したが、V8は32MiBのヒープ設定でも受け付けた。
- 配列をglobalに保持する追加probeでは、V8の使用ヒープ97,286,680 bytesを観測した。設定値とV8の報告上限はともに33,554,432 bytesで、上限callbackは発火しなかった。これは実行終了付近のJSヒープ統計であり、ピークRSSではない。
- 複数の配列を保持しながら継続確保する試験では、両候補が停止した。QuickJSはruntime-error、V8はホストによるisolate停止に伴うhost-error。どちらもstaged transactionは適用しない。
- V8の上限callbackは、終了を観測させるため128MiBの一時猶予を加える。この仕組みも厳密なprocessメモリ上限ではない。製品化前に単発確保とJS外の確保を含む資源制限方針を実装・検証する必要がある。

## 配布・保証範囲

- releaseビルドと両RustホストのClippy（全target、警告をエラー扱い）は通過した。実験コードのみを変更し、Desktopの製品コード・依存は今回変更していない。
- dumpbinで、両exeともVCRUNTIME140.dllとWindows/UCRT系依存を確認した。V8にはVCRUNTIME140_1.dll等の追加依存がある。クリーンな配布先PCでの動作は未確認。
- native I/Oは模擬モデルであり、実ファイル・HTTP・DOM/Excel・子プロセスの所有と停止を接続していない。Nodeの比較対象も実際のブラウザWorkerではない。その他の境界は27を引き継ぐ。

参考となる実装APIは[deno_core 0.412.0](https://docs.rs/deno_core/0.412.0/deno_core/)、V8のビルド資産は[rusty_v8公式説明](https://github.com/denoland/rusty_v8#binary-build)を参照する。実測は上記のローカル実験結果を優先する。

## 採用案と次のステップ

**現行のJavaScript互換性とコンパイラ実行を重視し、V8を製品CLIの実装先にする案を提案する。** 今回のV8構成で約54MiBのexeと、資源制限の追加整備を許容するかが判断点。QuickJSはサイズに利点があるが、今回の構成ではIntlを提供していない。どちらもWeb APIと実native I/Oへの接続が必要。

採用方針が決まったら、まず選択したホストの資源制限・背景処理・native要求所有の契約を固める。その後、共通部分を`packages/runtime-core`と`crates/native-core`へ段階的に移し、`.trk`読込・Work指定を持つRust CLI入口を追加する。
