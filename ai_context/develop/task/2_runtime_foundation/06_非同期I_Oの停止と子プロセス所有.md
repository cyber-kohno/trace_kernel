# 非同期I/Oの停止と子プロセス所有

2026-10-12。第4段階の継続。対象は外部プロセスとHTTPの非同期処理。CLIの追加、packages/cratesへの移動、同期ファイルI/O全体の変更は行っていない。

この文書は実施時点の記録。後続の `07_ファイルI_Oの境界と終了待ち.md` で、ファイル操作15コマンドを所有者へ追加し、読込等のエラー契約を修正した。scan・Excel等は引き続き未対応。

`05_Workerの実行ライフサイクル.md` は前段階の記録として残す。その文書で未実装としたnative停止のうち、今回対応した範囲は以下に限定する。

## 実行所有者

- `src-tauri/src/execution_io.rs` に、Tauriへ依存しないExecutionIoとOperationを追加した。実行ごとに処理を登録し、Operationの寿命でアクティブ件数を管理する。
- 停止時は新規登録を閉じ、既存Operationへ停止を通知し、全Operationの解放を待つ。通知はwatchの保持値なので、まだ待機に入っていないOperationも停止を見落とさない。
- cleanupの失敗は所有者に保持する。件数が0になっただけで「停止確認済み」とはしない。
- AppStateのExecutionContextへ所有者を持たせた。存在しないID・停止済みIDの処理開始は拒否する。worker_initのID重複も、既存contextを上書きせず拒否する。
- `worker_stop`: 非同期I/Oを停止・解放待ちする。表示用のchannel/DOMデータは残す。
- `worker_dispose`: 同じ停止確認をしてからcontextを削除する。停止失敗時はエラーを返し、contextを残す。

現在登録するコマンドは `run_process`、`load_http`、`load_html_from_url` の3つ。すべてのnativeコマンドがこの所有者に参加したわけではない。

## 外部プロセス

`src-tauri/src/process.rs` のrun_ownedはUI/Tauri Stateへ依存しない実処理になり、Tauri commandはOperation取得と呼び出しだけを担当する。

- タイムアウトを、標準入力の書き込み・stdout/stderrの受信・終了待ちまで含めて適用する。0と扱えない期限は起動前に拒否する。
- stdinへの書き込みとstdout/stderrの読み取りを並行して進める。子プロセスが出力パイプを満たしてからstdinを読む場合も詰まらない。
- stdinが空ならnullに接続してEOFを渡す。アプリのコンソール入力は継承しない。
- Cancel・タイムアウト・入出力失敗でcaptureを中止した後もChildを保持し、killと終了待ちを行う。その後にOperationを解放する。
- kill/終了待ちが失敗した場合はExecutionIoへcleanup失敗を記録し、正常終了にしない。
- kill_on_dropは、処理Futureが予期せず破棄された場合の補助策として設定する。通常の停止は明示的なkill/終了待ちを使う。
- WindowsではCREATE_NO_WINDOWで起動する。
- 引数・cwd・stdin encoding、stdout/stderr、非ゼロexitCode、stdoutのバイナリ検出は維持した。

**停止保証は直接起動した子プロセスまで。** 子プロセス自身が起動した孫プロセス、切り離したサービス、別アプリ等は所有・停止していない。Windows Job Objectや他OSのprocess groupなどを含む子孫の管理は、CLI公開前の残課題。

## HTTP

- ドメイン待機、リクエスト送信、ヘッダー受信、本文受信を停止・期限の対象にした。Cancellationで処理Futureを破棄し、その解放をOperation経由で確認する。
- native全体の既定期限は8秒。requestのtimeoutMsがある場合はその値を使う。既定期限もドメイン待機を含むため、以前の「送信から8秒」とは範囲が変わる。
- Timeout、Cancelled、ExecutionUnavailable、InvalidTimeoutをLoadErrorへ追加した。reqwest自身のタイムアウトもTimeoutへ揃える。
- URL/スキーム検証、query、method、headers、body、レスポンスmetadata、HTML種別検証、既存のサイズ判定は維持した。
- Future停止はローカルの待機を終えるもので、すでに相手サーバーが実行した処理を取り消さない。

## Desktopとの接続

- ContextDataUtilのprocessとDclNetはexecutionIdを付けてnativeを呼ぶ。ユーザー向け$process/$netの型や引数形式は変更していない。
- WorkerSessionも3つの対象コマンドのIDを自身の実行IDへ束縛する。別実行へ誤って登録しない。
- 対象APIではWorkerInvokeの一律10秒タイマーを使わず、nativeが期限と後片付けを所有する。25秒等の設定をWorkerの通信タイマーが10秒で打ち切る食い違いをなくす。他のコマンドの10秒待機は変更していない。
- done/runtime-error/Worker障害でWorkerを止めた直後にworker_stopを要求する。画面への終端通知はその停止確認を待つ。表示イベントが保留中でも、停止要求自体は先に開始する。
- ユーザー関数が対象native呼び出しをawaitせずに完了し、IPC応答が未完了だった場合は失敗にする。処理を停止した後、unfinished native I/Oと表示し、VFSをトランザクション画面へ渡さない。
- 停止失敗もdoneへ変換しない。cleanupFailedを表示側へ渡し、復旧snapshotを成功時と同様に消さない。
- 停止確認を待っている間にCancel・画面破棄・再実行した場合、旧失敗が新実行の画面へ届かないようID/所有者を照合する。

既存Workで$processや$netを呼び捨てにしていた場合、今後は正常終了扱いにならないことがある。確実に待つコードへ直す必要がある。ユーザー関数が意図的に例外をcatchし、対象処理が解放された後に継続することは引き続き可能。

## 保証外と次の優先項目

1. **同期ファイルI/O・scan・パーサー。** まだExecutionIoへ登録されない。Worker停止や10秒待機切れでOS処理を停止できるとはいえない。直接更新の副作用も巻き戻さない。読込失敗を文字列として成功返却する既存経路など、エラー契約も次に揃える。
2. **子孫プロセスとアプリ終了。** 今回は直接の子だけ。プロセスツリーと通常のアプリ終了を所有権へ結び付けることを検討・試験する。強制終了時にDropが走るという保証は置かない。
3. **資源上限。** process出力の累積上限、HTTP本文を読み終える前のサイズ制限、待機処理数の上限は未整備。
4. **停止待ちの方針。** OSのkill/終了待ちが返らない場合、今回の停止確認も待ち続ける。未確認の状態を成功扱いにして抜ける実装にはしていない。CLI向けには停止失敗・待機上限・終了コードの仕様が必要。
5. **UIとsnapshotの所有権。** アプリ全体で1つのsnapshot、StreamReceiverやsource mapの非同期寿命は前段階の残課題のまま。

これらを残したまま「第4段階完了」「native全体を停止可能」とはしない。まず同期ファイルI/Oのエラー・寿命の境界を優先する。その後に子孫/終了・資源制限を整理し、第5段階のWorkspace読込・実行準備分離へ進む。
