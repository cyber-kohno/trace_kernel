# トランザクション初期修正

この文書は第1段階の記録。サービス分離に関する最新状況は `03_トランザクションサービス分離.md` を参照。

## 実施内容

棚卸しA1-A5を対象に、既存の配置で回帰テストと修正を実施した。

- VFSのディレクトリ削除を `delete_dir` 命令へ変換。空ディレクトリのみを検証し、Rustの非再帰削除へ接続。
- ファイル削除を登録済みの `delete_file` へ接続。
- renameの検証と適用で同じ絶対宛先パスを使用。同一パスや同一ディレクトリ外へのrenameは拒否。
- 全件検証でerror/warningがあれば、適用を開始しない。
- 検証I/Oの例外を行の検証エラーへ変換。適用I/Oの例外は適用失敗へ変換。
- 適用失敗で停止し、後続行をskippedとして表示。成功・検証失敗・適用失敗をrunの結果として返す。
- 更新対象は読込時のmtime/sizeと元のテキスト内容を照合。全件検証と更新直前に検証し、読込中の変化も再度statで確認。
- 同じ適用結果を持つ行の再実行を拒否。検証段階の失敗は入力を直して再検証できる。
- トランザクション画面は閉じても適用結果を保持し、開き直した際の再適用を防止。
- 処理中のCloseを無効化し、トランザクション画面表示中のEscapeによる親画面破棄を抑止。二重Commitの防止とfinallyによる処理中表示の解除を追加。
- 作成と削除の両方を表示する行は `DirectoryRow.svelte` に改名。

## 現段階の保証

全件の事前検証に通った後、順番に適用する。最初の適用失敗で止まり、成功済み・失敗・未実行を区別する。
成功済みの処理は戻さない。部分適用を全体成功として扱わない。
ディレクトリ削除と配下の別操作が同じ計画に含まれる場合は、検証エラーとする。
ディレクトリ削除は再帰削除に拡張しない。

## 残課題

- JS側の照合とRust側の保存は別の操作。照合直後から保存までの競合を原子的に防ぐものではない。
- 新規作成・copy・renameの宛先競合も、事前検証とOS操作の間に変化し得る。
- decoded textによる比較は元のバイト列の完全一致を保証しない。原本のバイト保持・ハッシュ・ネイティブ側照合等は次の保証設計で判断する。
- 単一ファイルの原子的保存、複数ファイルのロールバック、永続的な適用記録は未実装。
- Worker終了・全体のcancel・外部processの寿命とGUI破棄の問題は、次の実行基盤整備で扱う。
- UIから独立したTransactionServiceとI/Oインターフェースの抽出は次の段階。packages/cratesへの移動、JSホストの選定、CLI追加は未実施。
- 自動のGUI操作試験は未実施。今回の画面変更は型チェックと依存経路の確認まで。
