## 初期固定上限

定数は `apps/desktop/src-tauri/src/resource_limits.rs` に集約した。今回UI設定や公開API引数は増やしていない。
以前はこれらの上限がなかったため、大きな正当な入力も新たに拒否され得る。実際のWorkの要求に応じた値の見直しは可能だが、切り詰めた成功に変更しない。

| 対象 | 上限 | 計測範囲 |
| --- | --- | --- |
| Excel入力 | 32MiB | 実際に読み取って保持するファイルバイト |
| Excel ZIP展開 | 合計128MiB、1エントリー16MiB | すべてのエントリーの展開バイト |
| Excel ZIPエントリー | 4096 | アーカイブ全体、未使用の付属ファイルも含む |
| Excelシート | 128 | 空シートも含むブック全体 |
| Excelセル | 合計100,000 | XLSXは空/重複のソースセルも含む。他形式はRange内の非Emptyセル |
| Excel矩形領域 | 合計1,000,000セル | 各非空シートの実セル最小/最大座標が囲む矩形。穴の空セルも含む |
| Excel文字列 | 各合計16MiB | XLSXの疎セルで保持する文字列と、出力セル値+シート名を別々の予算で計測 |
| 走査項目 | 100,000 | ルート1件+read_dirで列挙された全項目。除外・深度で非再帰・スキップリンクも含む |
| 走査ディレクトリ深度 | 64 | ルートを0とする再帰深度。深度64内のファイルは維持 |
| 走査名前 | 合計8MiB | ルートと全列挙項目の名前のUTF-8バイト。除外項目も含む |
| 走査条件 | dir/file合計128 | 条件コンパイル前に判定 |
| 走査pattern | 1条件4096バイト | UTF-8バイト数。Regex生成前に判定 |

上限ちょうどは正常な終端を確認できれば成功する。いずれも超過時は要求全体がエラーとなり、部分Book/Treeや途中切り詰めを成功値として返さない。
既存のHTTP本文2MiB、process出力合計16MiBは変更していない。

## Excelの処理境界

`parser/excel/limits.rs` はTauriに依存しない。入力はFileを8KiB単位で読み、既存LimitedBufferの追加前判定と確保失敗のエラー変換を使う。ファイルの広告サイズだけに依存しない。
ZIPはディスクへ展開せず、中央ディレクトリーのサイズを先に確認し、実際の展開ストリームも8KiB単位で数える。サイズ情報を小さく偽装しても実展開量の検査を通過できない。CRC/読込失敗もエラーにする。
ZIPでない形式は既存のcalamine自動判定へ渡す。ZIPの検査が正常に終わってからcalamineを開くので、XLSX/XLSB/ODS等のZIP入力には共通の展開量検査が先行する。
既存のzip 0.6.6をdev-dependencyから通常dependencyへ移した。新しい依存バージョンの取得・更新はしていない。

採用中のcalamine 0.23.1は、XLSXのworksheet_rangeで疎セルから密なRangeを確保する。小さいXLSXでもA1とXFD1048576に値を置くだけで大きな確保が起こり得る。
そこでXLSXについては公開worksheet_cells_readerを利用し、セル件数・座標・保持文字列・拡大中の矩形を検査した後でRange::from_sparseを呼ぶ。
XLSXの座標は行1,048,576/列16,384の範囲も確認する。dimensionの広告値だけでは拒否せず、実セルを使う。ソースセルを安定ソートし、重複座標は最後の非Empty値を維持する。
セルのデコード・数値/日付等の解釈はcalamineのまま。独自のXLSX値パーサーは作っていない。Book/Sheet/Row/Cell、0-based座標、maxRow/maxCol、空シートの省略、完全空文字セルの省略は維持する。

入力chunk・ZIPchunk・XLSXセル読込・DTO変換に協調停止checkpointを置いた。単一のOS読込やライブラリー呼出そのものを強制中断するわけではない。
Tauri受付/Operation所有/blocking処理終了待ちは10の契約を維持し、上限エラーでもOperationを解放する。

## 走査の処理境界

`scan.rs` にScanBudgetを追加した。進捗のcounterは従来どおり訪れたディレクトリ件数であり、資源予算の全列挙項目数とは区別する。
ユーザー指定limitDepthは従来の検索条件で、そこで再帰を省略する正常動作を維持する。一方、資源上限の深度64を超えて再帰しようとした場合はエラーにする。黙って64へ丸めない。
件数と名前量は選別前に数えるため、除外条件で大量の項目を走査する場合も制限される。ルート除外時の空ディレクトリ結果は維持する。
進捗イベントが既に届いていても、失敗した要求の部分Treeは返さない。編集画面は既存のエラー処理でlistener/search状態を解放し、不完全な新Treeを設置しない。
除外判定より先に再帰入口の深度を判定するため、深度65のディレクトリはそこで除外される条件でもエラーになる。limitDepthで再帰自体を止めた場合はこの判定へ到達しない。

## 保証の限界と次の工程

これは入力・論理領域・保持量の上限であり、アプリ全体のRSS、すべての割当、CPU時間を厳密に制限するsandboxではない。
ZIP中央ディレクトリーの解析、calamineの共有文字列/スタイル/metadataの読込、XMLの単一イベント、セル値の変換は内部で先に確保する。calamineの非公開DataTypeRefをDataTypeへ変換する際は、共有文字列1個のコピーが予算判定より先に起こり得る。
XLSXの密なRangeは確保前に守るが、XLS/XLSB/ODSはライブラリー内でRangeを先に確保し、戻った後に領域/セル予算を確認する。一部形式はopen自体でもシートを確保する。全形式の悪意ある入力に対するOOM/panic耐性を保証したとは扱わない。
共有文字列テーブルやオブジェクト/Vecの余裕容量、RangeとDTOの同時保持、IPCシリアライズ、Frontendへの複製、同時要求は別途メモリーを使う。既存形式の対応を突然XLSX限定へ狭めず、これらの限界を残した。
全形式で内部確保まで守るには、ライブラリー境界の追加検証/改善または独立プロセスとOS資源制限が別途必要。ライブラリー更新やプロセス分離は今回行っていない。
走査のOS列挙バッファ、進捗イベントの蓄積、IPC要求のJSON確保、長いrootPathは新しい上限の対象外。ファイルシステムsnapshot/TOCTOU対策にもならない。
既存のdirectory link非再帰方針を維持しているが、Windows junction、ACL、ネットワーク共有の待機について新たな保証はない。
上限で停止待機時間を保証しない。未解放処理をタイムアウトで消して成功にする設計にはしない。

次は実行ごとの同時native要求数を制限する境界を調べ、停止待機/通常終了の方針、他native処理の所有、snapshot/UI所有の残課題を整理する。
その後、第5段階のWorkspace読込・実行時検証・実行準備・API権限注入をUIから分離し、テストで守った共通packages/cratesへの移動と製品CLIへ進む。
