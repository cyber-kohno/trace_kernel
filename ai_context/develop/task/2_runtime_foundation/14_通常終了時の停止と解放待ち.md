# 通常終了時の停止と解放待ち

2026-10-13。第4段階の継続。13で調査した通常のメインウィンドウ終了経路に、新規受付の閉鎖、全実行への停止通知、実処理の解放待ちを追加した。
既存10〜13の変更を維持して追加した。commit/push、CLI追加、共通packages/cratesへの移動は行っていない。

## nativeの終了境界

`runtime.rs` のAppStateにアプリ終了用の受付ゲートと、executionIdなしの編集用ExecutionIoを追加した。
`shutdown_native_io` はexecutionsのMutex内でゲートを閉じ、編集用と既存全ExecutionContextのExecutionIoを取得し、全scopeへ先にcancelを通知する。その後にMutexを離して全scopeの解放を待つ。
一つのscopeの失敗を理由に、他scopeへの停止通知や解放待ちを飛ばさない。失敗はscope名付きでまとめて返す。

worker_initとnative I/O登録は同じMutexでゲートを確認する。終了開始と競合したworker_initは、停止対象に含まれるか受付前に拒否される。snapshot取得後に実行を再作成して抜ける経路を作らない。
終了開始後は新規Work、File15コマンド、走査、Excel、HTTP/HTML、processの受付を拒否する。既存のstop/disposeや出力取得は引き続き使える。
File/走査/ExcelのexecutionIdなしの呼出もOperationを登録する。通常の編集/Workspace/Transaction用I/Oは引き続き使え、Workごとの32枠制限は編集用scopeには適用しない。
終了開始後のIPCエラーはFile等では `Application native I/O is shutting down`、HTTP/HTMLではLoadError::ApplicationShuttingDownとし、容量超過や不明IDと区別する。

編集用blocking I/Oもcallerが破棄されたら完了扱いにするのではなく、blocking taskがOperationを所有して実処理の終了まで待つ。
終了待機を呼んだFutureが途中でabortされてもゲートは再開しない。後のshutdown呼出が同じscopeの終了を待てる。
shutdown自体はExecutionContextやrecovery snapshotを消さない。ただし並行するWorkerの正常disposeは、従来どおり解放後にそのcontextを削除するので、終了失敗時に全実行の出力を必ず残す保証ではない。

## 画面側の終了調停

`service/lifecycle/application-shutdown.ts` はUI/Tauriに依存しない終了サービスとし、確認、native停止、Worker停止、MCP停止、ウィンドウ終了を利用側が渡す。
`Entry.svelte` はWorkspace未設定/変更なしでもcloseイベントを同期的にpreventDefaultし、同じサービスを通す。未保存変更がある場合は従来の確認を先に行い、キャンセル時は停止・受付閉鎖を始めない。
確認中/解放待機中の重複closeは同じPromiseを共有する。二度目のcloseだけで未完了の停止待ちを通過しない。

承認後はnative/全Worker/MCPの停止をすべて開始してallSettledで待つ。同期例外でも他の参加者を飛ばさない。
すべて成功した後だけ再入closeイベントの通過を許可し、実際にWindow.closeを呼ぶ。close自体の失敗時には許可を取り消す。
失敗時はエラー表示とRetry closeを出し、ウィンドウを閉じない。承認後に受付を再開して通常作業に戻る機能や、一定秒数で強制exitする機能は追加しない。
Retryは完了判定を再試行するもので、記録済みcleanup failureを消さない。Workerの失敗したdisposeも保持するため、失敗原因によっては再試行しても閉じられない。

停止中は通常コンテンツをinertにし、キー操作、file-drop、新規MCP処理を拒否する。終了待機表示には明示的な文字サイズを設定し、従来レイアウトの高さを維持する。

## 全Workerの所有

`worker-lifecycle.ts` のregistryへDesktop WorkerAdapterのdisposeを登録する。stopAllは新規登録/init/startを閉じ、全所有者のdisposeを先に呼び、最後の解放まで待つ。
実WebWorkerのterminateとイベント解除は同期的に行うが、遅れて返るworker_initを待ってからnative worker_disposeを呼ぶ既存WorkerSessionの契約を維持する。
UIのonDestroy等で先にdisposeが始まった場合も、完了までは登録を残す。失敗したdisposeは登録を外さず、アプリ終了で見落とさない。
成功したdispose後は登録を解除できる。stopAllを重複呼出しても同じ結果を待ち、終了後の再実行は許可しない。

## 保証の限界と次の工程

対象はEntryのハンドラー登録後の通常メインウィンドウclose。OS強制終了、プロセスkill、WebView crash、直接Window.destroy、plugin-processのrelaunch、起動途中のclose等をこの完了保証に含めない。
OS/ライブラリー呼出の強制中断は追加していない。ファイルのOS待機やcalamine呼出が戻らない場合は、ウィンドウを開いたまま待つ。子孫プロセス、Rust process Futureの外部abort時の独立supervisorも従来どおり未実装。
DOM、channel/print等のOperation未登録native処理、開始済みUI非同期処理、snapshot更新、MCP request threadの全所有は未整理。MCPは既存stopコマンドの結果を待つが、その内部join/descriptor削除の失敗を完全に可視化する改修は今回していない。
recovery snapshotは今回新たに永続化したものではない。通常終了のshutdownはsnapshotを保存/削除する役割を持たず、強制終了後の復旧や失敗時の出力保存を保証しない。
編集用I/Oの追跡はアプリ全体の容量制限ではなく、受付前IPC queue、返却DTO、frontend Promise量やRSSの上限でもない。

手動確認では、Workspace未設定/変更なしの終了、未保存確認のキャンセル後の継続、実行中HTTP/process/Excel/走査での終了、close連打、終了待機表示と通常画面のレイアウトを確認する。
終了承認後はWork/編集用I/Oを再開できない仕様であることにも注意する。副作用のテストは一時ファイル/試験用Workで行う。
次は実GUIでの終了/Cancel/再実行の確認と、残るsnapshot/UI・他native処理の所有を優先し、その後に第5段階のWorkspace読込/検証/実行準備/API注入の分離へ進む。
