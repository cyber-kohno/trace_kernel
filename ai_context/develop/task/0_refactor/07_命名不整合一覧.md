# 命名不整合一覧

## 目的

現行アプリモジュール内の命名不整合を一覧化し、

- typo
- 大文字小文字 / 命名規則の揺れ
- 略語依存で意味が読みにくいもの
- 責務が名前から伝わりにくいもの

を切り分ける。

この資料は、Phase 6 の命名統一と局所改善の入力資料とする。


## 分類方針

本資料では、命名上の問題を以下の4つに分類する。

## A. typo

単純な綴り間違い、明らかな打鍵ミス。

## B. ルール揺れ

大文字小文字、接頭辞、ファイル命名規則の不統一。

## C. 略語依存

意味を知っている前提でしか読めない略称。

## D. 責務不明瞭

名前から責務やレイヤーが読み取りにくいもの。


## A. typo 一覧

## 高優先

### `MaintenanceMange.svelte`

- 現在名:
  - `MaintenanceMange.svelte`
- 想定:
  - `MaintenanceManage.svelte`
- 問題:
  - `Manage` の typo
- 影響:
  - ファイル探索時にノイズになる
  - UI の中核ファイルなので露出が高い


### `MDResourece.svelte`

- 現在名:
  - `MDResourece.svelte`
- 想定:
  - `MDResource.svelte`
- 問題:
  - `Resource` の typo
- 影響:
  - 関連ファイル探索の精度が落ちる


### `toastUtit.ts`

- 現在名:
  - `toastUtit.ts`
- 想定:
  - `toastUtil.ts`
- 問題:
  - `Util` の typo
- 影響:
  - util 系 naming の信頼性を下げる


## 中優先

### `trce_kernel`

- 現在名:
  - `package.json` の `name: "trce_kernel"`
- 想定:
  - `trace_kernel`
- 問題:
  - `trace` の typo
- 影響:
  - 配布名、識別子、ログ上の見え方に影響する可能性がある


### `idol`

- 現在名:
  - [PathState.svelte](app/src/app/util/form/validation/PathState.svelte) 内 status 値 `idol`
- 想定:
  - `idle`
- 問題:
  - state 名の typo
- 影響:
  - 実装者の理解コストが上がる


### `encorde`

- 現在名:
  - [dclFileSystem.ts](app/src/app/contents/detail/program/util/fs/dclFileSystem.ts) の declare 内 `encorde`
- 想定:
  - `encoding`
- 問題:
  - API declare 上の typo
- 影響:
  - API シグネチャの信頼性が下がる


## B. ルール揺れ一覧

## Store 系

### `storeEnv.ts` / `StoreProcess.ts` / `StoreResource.ts` / `storeWorkspace.ts`

- 問題:
  - `storeX.ts` と `StoreX.ts` が混在している
- 影響:
  - 一覧性が悪い
  - 命名ルールの判断コストが都度発生する
- 例:
  - `storeEnv.ts`
  - `storeDataset.ts`
  - `storeWorkspace.ts`
  - `StoreProcess.ts`
  - `StoreResource.ts`
  - `StoreSetting.ts`
  - `StoreWork.ts`
  - `StoreDeclare.ts`


### `storeLIcense.ts`

- 問題:
  - `LI` の大文字小文字が不自然
- 想定:
  - `storeLicense.ts` または `StoreLicense.ts`
- 影響:
  - typo に近いが、ルール揺れとしても悪目立ちする


## util 系

### `TypescriptUtil.ts`

- 問題:
  - 一般には `TypeScript` と表記するため、`Typescript` は揺れとして見える
- 想定:
  - `TypeScriptUtil.ts`
- 補足:
  - 社内規約で明示するなら許容も可能だが、標準表記とはずれる


### `streamAPI.ts`

- 問題:
  - `API` が大文字なのに、他の util は `camelCase` ベース
- 想定:
  - `streamApi.ts` もしくは `StreamApi.ts`


## TS / Rust 間の naming ルール差

### `file_system.rs` と `dclFileSystem.ts`

- 問題:
  - Rust は snake_case、TS は Pascal / camel が混在
- 補足:
  - 言語差として自然だが、橋渡し資料なしでは対応が追いにくい


## C. 略語依存一覧

## 高優先

### `MDEnv`, `MDProcess`, `MDWork`, `MDDataSet`

- 問題:
  - `MD` の意味がコード外の文脈なしでは読み取れない
- 想定:
  - `EnvEditor`
  - `ProcessEditor`
  - `WorkEditor`
  - `DatasetEditor`
 など
- 影響:
  - 画面編集系の役割が読み取りにくい


### `PREnv`, `PRProcess`, `PRWork`, `PRDataset`, `PRResource`

- 問題:
  - `PR` が何の略か伝わらない
- 実態:
  - 左側ツリーの parameter / record 表示系に見える
- 想定:
  - `EnvTreeItem`
  - `ProcessTreeItem`
  - `WorkTreeItem`
 など


### `tx`

- 対象:
  - `txCommitRunner.ts`
  - `txExecuter.ts`
  - `txPlanUtil.ts`
  - `TxDialog.svelte`

- 補足:

### `dcl`

  - `dclRuntime.ts`

## 中優先

### `PR`, `MD`, `tx`, `dcl` の混在

- 問題:

- 影響:

## D. 責務不明瞭一覧

## 高優先

### `store.ts`

- 問題:
  - 全体 store であることは分かるが、何の state を持つか名前から分からない
- 想定:
  - 将来的には `rootStore.ts` や責務別分割後の入口ファイル


### `global.ts`

- 問題:
  - 何を global にしているか不明
- 実態:
  - toast などのグローバル参照の保管先
- 想定:
  - `globalUiState.ts`
  - `globalRegistry.ts`
 など


### `fileUtil.ts`

- 問題:
  - file 全般の util に見えるが、実際は workspace 保存読込、gzip、title 更新まで持っている
- 影響:
  - 名前より責務が広すぎる


### `dataUtil.ts`

- 問題:
  - 非常に広い名前で責務が読み取りにくい
- 実態:
  - env 展開、CSV/TSV パース、バイナリ decode などが混在している


### `declareUtil.ts`

- 問題:
  - declare 生成だけでなく runtime API object 生成も持つ
- 影響:
  - 名前と責務がずれている


### `contextDataUtil.ts`

- 問題:
  - context data の util という抽象名で、注入データ構築、declare 生成、process 実行準備まで含む
- 影響:
  - 責務が広く読みにくい


### `workerAdapter.ts`

- 問題:
  - 実態は adapter というより bridge / controller に近い
- 影響:
  - 役割の期待値がずれる


### `MaintenanceMange.svelte`

- 問題:
  - typo だけでなく、何を manage しているのかが曖昧
- 実態:
  - 右ペイン編集対象の切り替えコンポーネント
- 想定:
  - `MaintenancePanel.svelte`
  - `EditorPane.svelte`
 などの方が実態に近い可能性がある


## 中優先

### `UsageUtil.ts`

- 問題:
  - 何の usage なのか不明
- 実態:
  - work 画面の注入利用情報表示補助と推測される


### `postUtil.ts`

- 問題:
  - post の意味が抽象的
- 実態:
  - Worker -> UI 間 state event の payload builder
- 想定:
  - `workerEventFactory.ts`
  - `runtimePostMessage.ts`


### `inspector.ts`

- 問題:
  - parser 配下なので文脈はあるが、何を inspect するかは名前単体だと弱い


### `StoreDeclare.ts`

- 問題:
  - declare という名前だけでは「共通 declare ソース」であることがやや分かりづらい


## 優先度別まとめ

## すぐ直してよい候補

影響が局所的で、意味も明確なもの。

- `toastUtit` -> `toastUtil`
- `idol` -> `idle`
- `encorde` -> `encoding`


## 先に設計方針を決めてから直す候補

命名規則全体とセットで判断したいもの。

- `storeEnv` / `StoreProcess` など Store 系
- `streamAPI`
- `TypescriptUtil`
- `storeLIcense`


## 構造改善とセットで直す候補

名前だけ直しても本質改善にならないもの。

- `store.ts`
- `global.ts`
- `fileUtil.ts`
- `dataUtil.ts`
- `declareUtil.ts`
- `contextDataUtil.ts`
- `workerAdapter.ts`
- `MaintenanceMange.svelte`


## 略語整理ポリシーの対象

- `MD*`
- `PR*`
- `tx*`
- `dcl*`


## 改名の基本方針案

## 1. typo は早めに直す

ただし公開参照点が多いファイルは、まとめて対応する。


## 2. Store 系は命名規則を先に決める

候補:

- すべて `camelCase`
- すべて `PascalCase`

中途半端に混在させない。


## 3. 略語は公開層ほど減らす

特に以下は可読性を優先した方がよい。

- 画面コンポーネント
- store
- bridge
- controller

逆に、transaction 配下の内部 util のようにスコープが狭い場合は、許容余地がある。


## 4. 責務不明瞭な名前は、構造改善と一緒に変える

たとえば `fileUtil` は単純改名より先に責務分割した方がよい。


## 現時点の結論

現行の命名問題は、単純な typo だけではなく、

- ルール不統一
- 略語前提
- 名前と責務のズレ

が重なって起きている。

そのため改善は、

1. typo 修正
2. naming rule 統一
3. 構造改善と連動した改名

の順で進めるのがよい。
