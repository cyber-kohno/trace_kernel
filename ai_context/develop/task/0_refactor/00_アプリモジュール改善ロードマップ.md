# アプリモジュール改善ロードマップ

## 目的

`app` 配下の Tauri アプリモジュールについて、  
機能追加を続けながら品質を高められる状態へ移行する。

本ロードマップでは、現時点の実装を前提に、  
「どこから着手すると効果が大きいか」を段階的に整理する。


## 現状の大きな課題

### 1. 命名規則が不安定

- `StoreProcess.ts` と `storeEnv.ts` のように、命名規則が混在している
- `MaintenanceMange`、`MDResourece`、`storeLIcense` など、タイポや大文字小文字の揺れが残っている
- コンポーネント名、ストア名、ユーティリティ名の付け方に一貫性がない

影響:

- ファイル探索がしづらい
- 新規実装時に命名判断コストが毎回発生する
- 設計の境界が名前から読み取れない


### 2. 状態管理の責務が集中している

- グローバル store が workspace、dialog、shortcut、cache、disable、license、setting をまとめて持っている
- UI状態とドメイン状態が分離されていない
- `$store` 全体を参照する実装が多く、依存範囲が広い

影響:

- 変更の影響範囲が読みにくい
- 不要な再評価や再描画が増えやすい
- テストしづらい


### 3. UIコンポーネントに責務が集まりすぎている

- `ProgramDialog.svelte` に実行制御、Workerイベント処理、進捗管理、出力管理、トランザクション表示が集中している
- 一部の画面コンポーネントが、表示だけでなくドメインロジックまで抱えている

影響:

- コンポーネントが肥大化しやすい
- 部分的な改修でも副作用が出やすい
- 実装者が入りづらい


### 4. utility / namespace にロジックが偏っている

- `FileUtil`、`ContextDataUtil`、`DeclareUtil` などに複数責務が混在している
- 変換、宣言生成、実行準備、I/O などが一か所に寄っている
- 役割よりも「とりあえず置く場所」として util が使われている

影響:

- 責務の境界が曖昧になる
- 再利用と差し替えがしにくい
- 実装の増築で複雑化しやすい


### 5. 状態更新がミューテーション寄りで追跡しづらい

- `push`, 直接代入, 配列の破壊的更新が多い
- 「どこで状態が確定したか」がコード上で追いにくい

影響:

- バグ調査時に追跡コストが高い
- 局所修正がしづらい
- リファクタ時に安全性を担保しにくい


### 6. フロントと Rust の境界がやや不統一

- Tauri invoke の呼び出し方が層ごとにばらついている
- 一部ラッパーが未整理、未完成のまま残っている
- Rust command と TS API の対応関係が見えづらい

影響:

- 呼び出し経路が増え、保守負荷が高い
- 失敗時のエラーハンドリング方針が揃わない
- API拡張時に設計が崩れやすい


### 7. 単一実行前提の実装が残っている

- Worker ID 固定など、暫定実装がある
- 並列実行や複数実行に対する拡張余地が狭い

影響:

- 将来的な機能拡張時に制約になりやすい
- 実行系の不具合原因になりやすい


## 基本方針

改善は、以下の順で進める。

1. 命名と構造のルールを決める
2. 状態管理の境界を分ける
3. 実行系の責務を分割する
4. フロントと Rust の API 境界を整理する
5. その後に局所最適なリファクタを進める

重要なのは、先に細部を直すのではなく、  
今後の変更が崩れにくい骨格を作ることである。


## フェーズ別ロードマップ

## Phase 1: 可視化とルール固定

### 目的

改善の前提となる命名規則、配置方針、責務境界を明文化する。

### やること

- ファイル命名規則を定義する
- Svelte コンポーネント、store、domain、infra、util の配置ルールを決める
- `app/src` 配下の役割マップを作る
- Tauri command と TS 呼び出し口の対応表を作る
- タイポ、表記揺れ、明確に悪い名前の棚卸しをする

### 成果物

- 命名ルール文書
- ディレクトリ責務一覧
- 改名対象一覧
- Rust command 対応表

### 完了条件

- 新規実装時に「どこへ置くか」「どう命名するか」で迷わない
- 既存の不整合箇所が一覧化されている


## Phase 2: Store の分割

### 目的

状態の責務を切り分け、UI状態とワークスペース状態を分離する。

### やること

- グローバル store の責務を分類する
- 少なくとも以下の単位に分割する

`workspace state`
ワークスペース本体、env/resource/dataset/process/declare/work

`ui state`
dialog、target、shortcut、toast、実行中表示など

`app state`
license、setting、起動引数、ハンドルパスなど

`runtime state`
実行進捗、stream、monitor、tx 状態など

- `$store` 丸ごと参照をやめ、必要な state だけ参照する形へ寄せる
- validation と disable 判定の責務を state と分離する

### 成果物

- 分割済み store
- store 依存マップ
- 主要画面の参照ストア見直し

### 完了条件

- 主要画面が必要最小限の store だけを参照している
- ワークスペース状態更新と UI 状態更新が分離されている


## Phase 3: 実行系の責務分割

### 目的

`ProgramDialog.svelte` を中心とした実行系の密結合をほぐす。

### やること

- 実行開始処理を controller に分離する
- Worker イベント処理を adapter / bridge 層に分離する
- stream 管理を専用 state / service に分離する
- transaction 表示制御を独立させる
- runtime error 整形処理を専用モジュール化する

### 分割イメージ

- `ProgramDialog.svelte`
  表示とユーザー操作に専念
- `programExecutionController`
  実行開始、停止、フェーズ遷移
- `workerBridge`
  Worker と Tauri invoke の仲介
- `streamStore`
  出力チャネルの状態管理
- `txController`
  VFS とトランザクションダイアログ制御

### 完了条件

- `ProgramDialog.svelte` が orchestration の薄い UI になる
- Worker 実行まわりのテストポイントが切り出される


## Phase 4: ドメインロジックの再配置

### 目的

`util` に偏っているロジックを、責務ごとに整理する。

### やること

- `FileUtil` の責務を分解する
  - workspace serialization
  - workspace file I/O
  - app title update
- `ContextDataUtil` を以下に分ける
  - context projection
  - runtime injection builder
  - monaco declare builder
- `DeclareUtil` を
  - API registry
  - declare generator
  - runtime object factory
 へ分割する

### 完了条件

- util が「雑多な置き場」ではなくなる
- モジュール名から責務が推測できる


## Phase 5: Tauri 境界の整理

### 目的

TypeScript と Rust の接続を安定化し、API 境界を保守しやすくする。

### やること

- invoke 呼び出し口を集約する
- command ごとの request / response 型を明示する
- エラーハンドリング方針を統一する
- 未使用 / 中途半端なラッパーを整理する
- Rust 側 command の粒度と命名を見直す

### 完了条件

- `TS -> bridge -> Rust command` の経路が統一される
- API追加時に迷いなく実装できる


## Phase 6: 命名統一と局所改善

### 目的

土台が整った後に、読みやすさと保守性を仕上げる。

### やること

- タイポ修正
- ファイル名と export 名の統一
- store ファイル名規約の統一
- 直接代入、破壊的更新の見直し
- 画面コンポーネントの props / callback 命名整理

### 完了条件

- 名前で迷う箇所が大幅に減る
- レビュー時に「命名と配置」の指摘が減る


## 優先順位

最優先:

- Phase 1 可視化とルール固定
- Phase 2 Store の分割
- Phase 3 実行系の責務分割

次点:

- Phase 4 ドメインロジックの再配置
- Phase 5 Tauri 境界の整理

仕上げ:

- Phase 6 命名統一と局所改善


## 進め方の提案

一気に大規模改修するのではなく、以下の単位で進めるのがよい。

### スプリントA

- 命名規則と配置ルールの文書化
- 改名候補の棚卸し
- store 責務分類

### スプリントB

- store 分割
- `$store` 直接依存の削減

### スプリントC

- `ProgramDialog` 周辺の分割
- Worker / stream / tx の整理

### スプリントD

- util 再編
- Tauri bridge の集約

### スプリントE

- 命名統一
- 残課題の局所改善


## 最初の着手対象

最初の一手としては、以下を推奨する。

1. `app/src` の責務マップを作る
2. store を責務別に分割する設計案を作る
3. `ProgramDialog.svelte` の責務一覧を出し、分割単位を決める

この3つができると、以後の改善は「思いつきの修正」ではなく、  
明確な設計方針に沿って進められる。


## 補足

現行モジュールは、機能自体はかなり揃っている。  
そのため、問題は「未実装」よりも「構造化不足」に寄っている。

したがって、

- 機能追加を止めず
- 実行系の中核を壊さず
- 段階的に責務を分離する

という進め方が最も現実的である。
